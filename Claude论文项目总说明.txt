项目名称：鼓浪屿智慧导览系统

一、项目定位与研究背景

本项目是一个面向鼓浪屿历史街区导览场景的智慧导览系统，重点服务对象包括普通游客、老年游客以及视障用户。项目不仅关注“能否到达目的地”，更强调在复杂历史街区中提供安全优先、无障碍友好、可解释、可交互的导览体验。

项目选题的现实背景包括以下几点：
1. 鼓浪屿属于典型历史风貌街区，道路狭窄、坡道与台阶较多、建筑密集、游客流量较高，传统地图式导航对视障群体和行动不便群体支持不足。
2. 现有通用导航产品往往更关注最短路或通行效率，较少显式建模坡度、摩擦系数、路面材质、高差等无障碍风险因素。
3. 针对旅游导览的智能问答系统很多依赖纯大模型回答，容易脱离本地场景知识，缺乏针对具体景点、具体路段和具体安全提醒的可靠性。
4. 视障导览不应只停留在语音播报层面，还应结合建筑历史、触觉信息、气味提示、环境音提示与安全提醒，形成多模态、具场所感的导览体验。

因此，本项目的核心目标不是做一个普通旅游 App，而是构建一个“面向无障碍场景的研究型智慧导览原型系统”，验证以下问题：
1. 是否可以基于本地道路图和路况属性实现安全优先导航。
2. 是否可以将本地知识库与外部大模型结合，提高景区问答和导航解释的可用性。
3. 是否可以通过语音交互、环境描述、触觉/气味提示等方式增强视障用户对空间的理解。
4. 是否可以通过实验数据说明安全优先策略相较普通路径规划具有实际价值。

二、项目当前完成度

本项目当前已经不是概念设计，而是完成了一个可运行、可演示、可测试、可用于论文撰写的原型系统，主要包括：
1. 前端界面与多页面交互。
2. 后端接口服务。
3. 本地 SQLite 数据库。
4. 路径规划引擎。
5. 景点知识问答与导航问答。
6. 语音输入与语音播报。
7. 后台分析与 A/B 测试统计支持。
8. 与 Unity 场景实验相关的数据统计结果。

从研究与论文角度，本项目已具备完整系统闭环和实验支撑，适合作为“系统设计 + 算法策略 + 实验评估”类型的计算机论文基础。

三、系统总体架构

1. 前端技术栈
- React
- Vite
- 部分图表组件使用 Recharts
- 浏览器端使用 SpeechRecognition / webkitSpeechRecognition 做语音识别
- 浏览器端使用 speechSynthesis 做语音播报

2. 后端技术栈
- FastAPI
- Python
- OpenAI 兼容 SDK 调用 DashScope / 通义千问接口
- NetworkX 用于图结构路径规划

3. 数据层
- SQLite 本地数据库 `backend/gulangyu.db`
- 数据表包括建筑表、无障碍节点表、道路表、访问日志表、危险日志表、A/B 测试汇总表等

4. AI 能力来源
- 系统不是纯本地模型
- 系统通过 DashScope 的 OpenAI 兼容接口连接通义千问模型
- 同时结合本地 SQLite 知识数据进行增强
- 因此整体属于“本地知识 + 外部大模型 API”的混合架构

5. 典型调用链路
- 前端用户在页面输入文本或发起语音提问
- 前端将消息、用户朝向、ASR 置信度、会话上下文发送到后端 `/api/chat`
- 后端先分析导航意图，再结合本地数据库中的建筑、节点、道路信息进行匹配
- 若为导航请求，则执行地点识别、起终点匹配、路径计算，并生成解释性回复
- 若为知识问答请求，则组织本地知识并调用外部大模型生成回答
- 后端返回文本回复、调试信息、会话状态
- 前端显示消息并触发语音播报

四、系统核心模块

（一）景点与空间知识库

系统内置鼓浪屿典型景点与无障碍导览信息。当前建筑数据约 7 个核心建筑，包括：
1. 协和礼拜堂
2. 许家园
3. 黄荣远堂
4. 海天堂构
5. 天主堂 / 天主教堂
6. 李传别宅
7. 仰高别墅

每个建筑记录了如下信息：
- 名称
- 地理位置
- 所属区域
- 图片
- 历史介绍
- 气味描述
- 触感/材质描述
- 安全提示
- 经纬度

这使系统不仅能回答“是什么建筑”，还能回答“这里摸起来是什么感觉”“有什么危险”“周围环境有什么气味或声音”等，体现对视障导览场景的针对性。

（二）无障碍节点与道路建模

系统使用本地数据库中的节点与道路构建可导航图。

1. 节点数据
- 当前约 22 个节点
- 包括建筑入口、路口、转角、休息点等类型
- 每个节点包含名称、经纬度、环境音、气味、详细描述等信息

2. 道路数据
- 当前约 26 条边
- 每条道路记录如下属性：
  - 起点与终点节点
  - 路面材质
  - 宽度
  - 坡度
  - 摩擦系数
  - 路段说明

这种建模方式使系统能够显式考虑无障碍通行风险，而不是仅以最短几何距离为目标。

（三）路径规划引擎

后端 `graph_engine.py` 中实现了路径规划核心逻辑，主要特点如下：

1. 使用 NetworkX 构建图结构。
2. 使用 Haversine 公式根据节点经纬度计算真实距离。
3. 针对不同用户类型定义差异化权重模型。
4. 支持“最安全路径”和“最短路径”两种策略。
5. 支持候选路径生成与多路径去重。
6. 能根据手机朝向生成更自然的转向提示。

当前使用的用户画像包括：
- normal
- elderly
- disabled
- blind

当前边权计算综合考虑：
- 距离
- 坡度
- 摩擦系数
- 用户类型差异

例如，对于 blind、disabled、elderly 等用户，系统会对坡度和低摩擦风险赋予更高惩罚，以体现安全优先导向。

（四）导航语义识别与鲁棒匹配

项目的一个重要亮点是针对语音输入中的识别误差做了较强的容错设计。后端 `main.py` 中实现了较完整的地点匹配与导航意图识别逻辑，主要包括：

1. 导航意图关键词检测
- 如“从”“到”“去”“前往”“怎么走”“导航”“带我去”等

2. 别名词典
- 例如“海天”匹配“海天堂构”
- “协和”匹配“协和礼拜堂”
- “天主堂”匹配“天主教堂”
- “羊羔别墅”匹配“仰高别墅”

3. 拼音匹配与前缀匹配
- 对景点名及用户输入进行拼音转换
- 适配同音字、近音字和缺字跳字输入

4. 模糊匹配
- 使用 difflib.SequenceMatcher 进行字符和拼音窗口匹配
- 根据别名长度和 ASR 置信度动态调整阈值

5. 多场景容错
- 标准输入
- 同音字错误
- 缺字跳字
- 别名输入
- 单终点导航
- 非导航闲聊

从论文角度，这一模块可归纳为“面向景区语音输入场景的鲁棒地点识别方法”。

（五）AI 问答模块

系统 AI 问答不是简单把用户话术直接转给大模型，而是采取“本地知识增强 + 外部模型生成”的方式。

其特点如下：
1. 后端先从本地数据库读取建筑、节点、道路等结构化知识。
2. 针对导航类问题先识别起点、终点、路线策略和安全信息。
3. 针对一般景点问答，再结合景点知识和上下文调用外部大模型生成回复。
4. 前端保存最近若干轮对话，作为 `conversation_history` 发送给后端。
5. 后端返回 `session_state`，前端保留单窗口内的连续对话状态。

这意味着系统已经从“单轮问答”演进为“带上下文状态的多轮问答原型”。

（六）语音交互模块

前端 `AiPage.jsx` 已实现以下能力：
1. 浏览器端语音识别。
2. 浏览器端语音播报。
3. 与后端 AI 导航问答接口联动。
4. 手机端方向传感器读取用户朝向。
5. 多轮会话历史发送。
6. 适合手机端的聊天容器滚动与显示逻辑。

语音导览对论文的意义不只是“多了一个按钮”，而是体现系统面向视障使用场景的自然交互方式。

（七）前端展示与场景体验模块

前端除了 AI 页面外，还包含：

系统整体已具备“研究原型系统”所需的可演示性。

七、关键实验与结果

（一）语音导航识别与鲁棒性压测

项目包含一套专门的测试脚本 `backend/stress_test.py`，构造了 30 条种子测试用例，并扩充为大规模测试集合，用于验证导航语义识别的可靠性。测试场景包括：
1. 标准输入
2. 同音字错误
3. 缺字跳字
4. 别名输入
5. 单终点导航
6. 非导航闲聊

根据现有报告 `stress_test_report_20260327_091208.txt`，核心结果为：
1. 意图识别准确率：100.0%
2. HTTP 成功率：100.0%
3. 算法识别成功率：100.0%
4. 相对基线提升：+50.0%
5. 平均响应时间：430ms
6. P50：476ms
7. P90：663ms
8. P99：756ms
9. <=500ms 占比：70.0%

这一结果说明：
1. 在场景识别和地点容错识别方面，系统效果较强。
2. 在鲁棒性与可用性方面，算法相较直接字符串匹配基线明显提升。
3. 在响应速度方面，识别正确但时延仍有优化空间，这一点可以在论文中如实写为局限性与后续优化方向。

（二）A/B 实验统计结果

项目当前还有针对 Unity 场景或仿真测试的 A/B 实验结果，已有文本统计摘要 `paper_ab_statistics.txt`。

已知关键结果如下：

1. 样本情况
- 固定样本 ID 共 10 个
- 有效轮次：10

2. 危险提示代理占比
- A 组：97.00% ± 9.49%
- B 组：0.00% ± 0.00%
- 均值差：97.00 个百分点
- Wilcoxon p 值：0.000977
- Cohen's dz：10.2247

3. 路径长度
- A 组：311.28 ± 2.93 m
- B 组：389.49 ± 7.28 m
- 均值差（B-A）：78.21 m
- 配对 t 检验 p 值：0.000000
- Cohen's dz：15.6718

4. 完成时间
- A 组：97.26 ± 1.68 s
- B 组：140.07 ± 5.46 s
- 均值差（B-A）：42.81 s
- 配对 t 检验 p 值：0.000000
- Cohen's dz：8.9567

5. 结论建议
- B 组将危险提示代理占比从 97.0% 降至 0.0%，同时带来 78.2 m 的路径增长与 42.8 s 的时间增加。

从这些数据可以得出的论文级表述方向包括：
1. 更强调安全规避的策略可以显著降低危险暴露。
2. 安全性提升往往以路径增长和时间增长为代价。
3. 因此本项目的核心不是单纯最短路，而是“安全性-效率”之间的平衡与任务目标重构。

如果写论文，这部分很适合成为实验章节中的重点量化结果。
